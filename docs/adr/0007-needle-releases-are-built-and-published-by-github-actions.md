# needle releases are built and published by GitHub Actions

needle lives in `needle/` (the app in `needle/app/`, the engine in `needle/engine/`) so one path is the package. release-please watches the conventional commits that touch `needle/` and keeps one release PR open: the next version (from `feat:` and `fix:`; pre-1.0, a breaking change bumps the minor) and a changelog in `needle/CHANGELOG.md`. Merging that PR is the one manual step. It tags `needle-vX.Y.Z` and creates the GitHub Release; `needle-release` then builds the package with `makepkg` in an `archlinux:base-devel` container (`check()` runs both test suites), signs it, and publishes it twice: as assets on the Release (package, detached `.sig`, `SHA256SUMS`, the signing key) and as an OCI artifact at `ghcr.io/kurtlieber/needle:X.Y.Z` and `:latest`, which is what the repo's Packages panel lists. GHCR has no pacman package type, so the artifact is the `.pkg.tar.zst` itself, pulled with `oras`. `needle-ci` builds the same package unsigned on every PR and push that touches `needle/`.

The version has one source, `needle/VERSION`, which release-please bumps along with `pkgver` in the PKGBUILD. qmake passes it to the app and the engine's `build.rs` passes it to the engine, so `Cargo.toml` and `Cargo.lock` never change for a release. The PKGBUILD builds from a source tarball of `needle/` (`bin/source-tarball`, which `bin/install` and CI both run), so going to the AUR is a change of `source=` to the tag's archive, not a rewrite.

Packages are signed with a dedicated ed25519 key, "needle package signing" (`E5278B2148A2833AB898C69FC5A7379D20ECB792`, expires 2029-10), held in 1Password and in the secret `NEEDLE_SIGNING_KEY` of the `release` environment, which only `main` may use; only the publish job names that environment, so no branch or PR build can read the key; the public key is `needle/app/pkgbuild/needle-signing-key.asc`. The repo is private, so every download needs a GitHub login (`gh release download` or `oras login ghcr.io`) until it goes public.

**Considered Options**: GitHub Releases only (the usual home of Arch packages, but the Packages panel stays empty); GHCR only (no changelog page or plain download); a tag pushed by hand (a person picks every version); a release on every merge to main (no gate before a release); release-please on the repo root with `exclude-paths` (it can only exclude directories, so a backend commit touching `README.md` or `pyproject.toml` would count as a needle change); bumping `Cargo.toml` per release (`Cargo.lock` holds the crate's own version, and `cargo build --locked` would fail on the mismatch); a pacman repository database (pacman cannot authenticate to a private repo's downloads; it waits for the repo to go public or for the AUR).

**Consequences**: commits that touch `needle/` follow conventional commits, or they leave no changelog entry and no version bump. The release PR is opened with `GITHUB_TOKEN`, so `needle-ci` does not run on it; the release build is the check. The repo needs "Allow GitHub Actions to create and approve pull requests" on. Environments and rulesets on a private repo need GitHub Pro: rulesets keep `needle-v*` tags from being moved or deleted and `main` from being force-pushed or deleted. A ruleset requiring `needle-ci` is left out, because it would block every release PR. GHCR's free private storage is 500 MB; a release is about 5 MB. Rotate the signing key before it expires: a new key in the secret, 1Password and the repo, published with the next release.

**Update, 2026-10**: needle moved to a repository of its own. Its files are at the root (`app/`, `engine/`, `VERSION`, `CHANGELOG.md`), release-please covers the whole repository, and tags are `vX.Y.Z`; releases up to 0.3.0 were tagged `needle-vX.Y.Z` in the earlier repository. Everything else above stands.
